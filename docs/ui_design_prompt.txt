## 🧩 AYLETNA SCREEN DESIGN & COMPONENT SYSTEM

The external prototype folder has been retired. The current design source is now:

1. **`prd.md`** for product behavior, roles, flows, and acceptance criteria.
2. **`color_list_chat_gpt.txt`** for all color values.
3. **Existing implemented Flutter screens in `lib/screens/`** for approved layout direction.
4. **Shared Ayletna widgets in `lib/widgets/`** for reusable branded components.

Future implementation must not reference retired external prototype assets. The app has already copied the useful screen design direction into Flutter; new work should unify those screens into a smaller, consistent Ayletna component library.

### Brand & naming

- Product name: **Ayletna Restaurant** / **مطعم عيلتنا**.
- App bar / about / web manifest title: `Ayletna Restaurant`.
- Default locale: Arabic (`ar`) with RTL-safe layout.
- Currency: **JOD**.
- Logo / favicon: `assets/images/logo_falafel.png` via `WidgetsLogoIcon` where a brand mark is needed.
- Never use old prototype names as product branding. If existing l10n keys still contain legacy prototype naming, replace them when touching that screen.

### Unified component principle

Do **not** create a separate card/widget type for every screen. Use a small set of flexible, branded primitives:

| Component | File | Purpose |
|-----------|------|---------|
| App button | `widgets_app_button.dart` | Primary, secondary, outline, ghost, danger, success, full-width, icon-leading/trailing, disabled |
| Icon button | `widgets_icon_button.dart` | Consistent icon-only actions, app bar actions, circular/tonal variants |
| App card | `widgets_app_card.dart` | Default card shell for most content: padding, radius, border, optional accent strip/header/trailing/action |
| Metric card | `widgets_metric_card.dart` | KPI, balance, count, revenue, inventory, shift, and report metrics |
| Choice card | `widgets_choice_card.dart` | Selectable options: address, payment, order type, condition, role, preference |
| App bar | `widgets_app_bar.dart` | Branded role-aware app bars with title, leading, actions, avatar/search/notification patterns |
| Bottom navigation | `widgets_bottom_navigation.dart` | Shared `NavigationBar` with role presets and selected index |
| Action bar | `widgets_action_bar.dart` | Sticky bottom CTA area for checkout, payment, refund, return, kitchen prep, and step flows |
| Page header | `widgets_page_header.dart` | Eyebrow/title/subtitle/action block at the top of screen content |
| Status pill | `widgets_status_pill.dart` | Status, role, tier, order-type, availability, selected-state labels |
| Info banner | `widgets_info_banner.dart` | Success, warning, info, policy, deposit, fair-wage, and validation notices |
| Step progress | `widgets_step_progress.dart` | Step headers, progress lines, wizard indicators |
| List item | `widgets_list_item.dart` | Repeated rows for transactions, staff, orders, audit events, inventory, settings |
| Amount line | `widgets_amount_line.dart` | Label/value amount rows with JOD and semantic finance colors |
| Financial summary | `widgets_financial_summary.dart` | Checkout/refund/deposit/tips/revenue summary blocks |
| App text field | `widgets_app_text_field.dart` | Text input, search input, amount input, QR/order lookup fields |
| Filter chip | `widgets_filter_chip.dart` | Filter tabs/chips with one selected-state design |

If one of these files does not exist yet, create or upgrade it before adding another screen-local variant. Keep existing useful widgets, but align them with this system over time.

### Card unification rule

Use **`WidgetsAppCard`** as the default shell. Do not create separate branded card classes like `ProfileCard`, `StaffCard`, `TransactionCard`, `TaskCard`, `WalletBalanceCard`, or `ProductCard` unless they are truly reusable domain components with behavior beyond presentation.

Compose content inside `WidgetsAppCard` using:

- `WidgetsListItem`
- `WidgetsStatusPill`
- `WidgetsMetricCard`
- `WidgetsAmountLine`
- `WidgetsFinancialSummary`
- `WidgetsChoiceCard`
- `WidgetsIllustrationPanel`

### Button unification rule

All buttons must use **`WidgetsAppButton`** or global `FilledButtonTheme` / `OutlinedButtonTheme` styles. Screens must not define ad-hoc `FilledButton.styleFrom(...)`, `OutlinedButton.styleFrom(...)`, custom local heights, local radii, or local font weights unless the change is promoted to the shared button widget/theme.

### Icon button unification rule

App bar actions, circular buttons, QR buttons, search buttons, and more-menu actions must use **`WidgetsIconButton`** or a shared app bar variant. Icon-only interactions must have consistent size, hit target, radius, tonal background behavior, and semantic labels where appropriate.

### Per-screen workflow

For each PRD screen or redesign task:

1. Read **`prd.md`** §5–6 for the product behavior and route.
2. Inspect the existing related Flutter screen(s) in `lib/screens/<role>/`.
3. Identify reusable widgets from the component system above before writing screen-local widgets.
4. Implement with **`CoreTheme`**, **`CoreColors`**, **`CoreSpacing`**, **`CoreTypography`**, **`Widgets*`**, and **`AppLocalizations`**.
5. If a new repeated pattern appears twice, extract or plan extraction into `lib/widgets`.
6. Verify [PRD §15.8 checklist](#-prd-158--ui-acceptance-verify-before-merge).
